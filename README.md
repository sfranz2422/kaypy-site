# kaypy-site

The kaypy website: the guide, the API reference, the tutorials, and a
playground you can write a game in.

**There is no backend.** Not "a small one" — none. Everything the playground
does happens in the visitor's browser: Pyodide brings Python, kaypy is written
into its filesystem as files, and the sprite packs are fetched like any other
static asset. So this deploys as a Render **Static Site**, costs nothing to
run, and has nothing that can be down.

## Deploying

Render → New → Static Site → this repo.

| | |
|---|---|
| Build command | *leave it empty* |
| Publish directory | `dist` |
| Environment variable | `SKIP_INSTALL_DEPS` = `true` |

`SKIP_INSTALL_DEPS` because Render otherwise detects `requirements.txt` and
pip-installs markdown and pygments on every deploy — for nothing, since
`dist/` is prebuilt. That is added build time and one more way for a deploy to
fail on a morning nobody touched anything.

**Render serves `dist/404.html` for a missing path on its own.** Verified on
the live site; no rewrite rule needed. (Their docs do not say so, hence the
note.)

**A `.app` domain is HSTS-preloaded**, so browsers refuse it over plain HTTP,
always. While DNS propagates and before the certificate is issued you get a
TLS error page rather than the usual "site can't be reached" — expected, and
not a sign the DNS is wrong. GoDaddy has no ANAME/ALIAS, so the apex is an
`A` record to Render's load balancer and `www` is a `CNAME`.

**The empty build command is deliberate.** `dist/` is generated by `build.py`
and committed, so Render only ever serves files. A static site that needs a
working Python toolchain on someone else's builder is a static site that can
break on a morning you did not touch it, in the middle of a lesson, for
reasons that have nothing to do with you.

## Working on it

```bash
python3 build.py          # content/ + templates -> dist/
python3 build.py --serve  # ...and serve it at http://127.0.0.1:8000
```

Then commit `dist/` along with whatever you changed. `build.py --check` fails
if `dist/` is out of date, which is what stops a commit that edits the source
and forgets the output.

## Where things come from

Most of this repo is written here. Two things are not, and are vendored
instead, because they already exist and having two copies drift apart is the
failure that costs a lesson:

```bash
python3 vendor.py         # from ~/pyide
```

| vendored | from | why |
|---|---|---|
| `dist/engine/kaypy_bundle.json` | `pyide/static/py/` | the engine the playground runs |
| `dist/assets/` | `pyide/static/assets/` | the sprite packs and sounds |
| `dist/play/game.js`, `export.js`, `sprites.js` | `pyide/static/` | the parts of the editor that are not UI |

`vendor.py` writes `dist/engine/stamp.json` saying which kaypy version and
which PyIDE commit it took them from, so a bug in a built game can be traced
to a source tree rather than guessed at.

What is **not** vendored is the editor shell itself — Run, Stop, the Sprites
panel, Export. PyIDE's is wound through accounts, autosave, assignments, tabs
and console mode, none of which exist here. The playground's shell is its own,
and small.

## Layout

```
content/          the markdown: guide, api, tutorials
templates/        the page shell and the nav
play/             the playground's own shell (its JS and CSS)
static/           css, the logo, favicons
build.py          content -> dist
vendor.py         pyide -> dist
dist/             what Render publishes. Generated, and committed.
```
